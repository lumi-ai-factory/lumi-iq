## 1. Compliance with LUMI Supercomputer Operational Policies

To ensure full compliance with the **LUMI Acceptable Use Policy**, **LUMI Security Guidelines**, and **LUMI Lustre File System Best Practices**, the software stack incorporates the following core requirements:

### 1.1 Storage & Lustre Filesystem Policy (Tykky Container Wrapper)
* **Lustre I/O Protection:** Standard Python virtual environments and Conda installations generate tens of thousands of individual files, metadata operations, and small inodes. On high-performance parallel file systems like Lustre on LUMI, this causes severe metadata server contention and degrades storage performance for all cluster users.
* **Tykky Mandate:** In strict adherence to LUMI policies, all hybrid software environments deployed under LUMI-IQ must be packaged using the **LUMI Container Wrapper (`Tykky`)** (`pip-containerize` or `conda-containerize`). This encapsulates the entire dependency tree into a single, high-performance compressed SquashFS image mounted read-only during job execution.
* **Lmod Integration:** Software packages are exposed to end-users via the hierarchical Lmod environment module system under the standardized naming scheme: `LUMI-IQ-<module_name>/<backend_target>`.

### 1.2 Authentication & Cybersecurity Policy
* **Prohibition of Hardcoded Credentials:** In compliance with LUMI General Terms of Use and EuroHPC cybersecurity standards, credentials, passwords, and tokens must **never** be hardcoded into scripts, Jupyter notebooks, or committed to version control.
* **Two-Tier Authentication Architecture:**
  * *Classical Access:* Mediated via LUMI user accounts, SSH key pairs (Ed25519/RSA), and MyAccessID federated authentication via LUMI Open OnDemand.
  * *Quantum Access:* Mediated over HTTPS via LEXIS Platform Keycloak OIDC JWT tokens. Tokens are managed dynamically using the OAuth 2.0 Device Flow (interactive browser verification in Jupyter/CLI) or via scoped environment variables (`export LEXIS_TOKEN`), with Personal Access Tokens (PAT) slated for future releases.

### 1.3 Batch Scheduling Policy (Slurm Workload Manager)
* Standard batch execution on LUMI compute nodes must explicitly specify resource accounting parameters (`--account=project_...`), proper partition selection (`standard`, `small`, or `gpu`), node/CPU topologies, and execution time bounds.

### Section 2.2: Quantum Session Locking & Operational Policy (Addressing Comment `[JT3]`)

In iterative hybrid workflows (such as VQE or QNNs), dispatching hundreds of individual circuits through a conventional batch queue introduces intolerable latency. The QScheduler engine resolves this by providing **Quantum Session Locking**. The operational policy governing these sessions is defined as follows:

* **Session Allocation:** A hybrid job requests an exclusive quantum session with a requested walltime window. Once active, circuit submissions bypass the general queue and execute directly on the QPU control interface with sub-second turnaround.
* **Early Session Completion:** If an algorithm reaches mathematical convergence before the reserved session duration expires, the client SDK invokes an explicit session release (`session.close()`), or the QScheduler watchdog detects socket termination. The exclusive lock is immediately revoked, and the QPU instantly reverts to serving the multi-tenant general queue, preventing resource idle time.
* **Exceeded Session Walltime (Hard Limit Enforcement):** To prevent hardware monopolization and ensure fair-share allocation across European consortia, QScheduler enforces strict hard walltime ceilings. If a session exceeds its allocated window, in-flight circuits are completed, subsequent iterative requests within the session are rejected, and the lock is revoked. The user algorithm can either fall back to standard asynchronous queued execution or schedule an additional session.

### Section 2.4: Quantum-as-a-Service (QaaS) & Updated Code Example (Addressing Comments `[JT4]`, `[JK5]`, `[JT6]`, `[JT25]`)

Execution of quantum circuits on physical QPUs is mediated by the Quantum as a Service (QaaS) client framework developed at IT4Innovations. The client package and its dependencies are hosted on the IT4Innovations package registry and installed as follows:

```bash
pip install qaas[iqm_qiskit] --extra-index-url https://opencode.it4i.eu/api/v4/projects/107/packages/pypi/simple
```

#### Updated & Verified Python Code Example

```python
import os
import time
from qiskit import QuantumCircuit
from qheappe_client.qprovider import QProvider

# 1. Initialize QProvider with LEXIS authentication and project allocation
# In interactive mode, omitting 'token' opens a browser login; in batch mode, provide LEXIS_TOKEN.
provider = QProvider(
    lexis_project="vlq_qaas_project",
    token=os.getenv("LEXIS_TOKEN"),
    lexis_api_url="https://api.lexis.tech",
)

# 2. Connect to the production VLQ backend via the QScheduler resource
resource_name = "VLQ-CZ-dev-P0003"
backend = provider.get_backend(
    lexis_resource=resource_name,
    backend_name="VLQ",  # Production 24-qubit Star-topology QPU
)
print(f"Connected to QPU Backend: {backend.name} on resource {resource_name}")

# 3. Construct quantum circuit (e.g., Bell state preparation)
qc = QuantumCircuit(2, 3)
qc.h(0)
qc.cx(0, 1)
qc.measure([0, 1], [0, 1])
qc.h(0)
qc.measure(0, 2)

# 4. Transpile circuit for the native Star-topology coupling map and basis gates
qc_transpiled = backend.transpile(qc)

# 5. Dispatch job to QScheduler
job = backend.run(qc_transpiled, shots=1024, job_name="lumi_iq_bell_demo")
print(f"Job dispatched successfully. Job ID: {job.job_id()}")

# 6. Await job execution (blocks until terminal state: FINISHED, FAILED, CANCELED)
result_legacy = job.result(qiskit_legacy=True, with_measurements=True)
counts_legacy = result_legacy.get_counts()
bitstrings_legacy = result_legacy.get_memory()

# Modern Qiskit primitive format
result_primitive = job.result(with_measurements=True)
counts_primitive = result_primitive[0].data.meas.get_counts()

print("Execution Results (Legacy):", counts_legacy)
print("Execution Results (Primitive):", counts_primitive)
```

### Section 3.3 & Section 5: Role of Classical Shadows (Addressing Comments `[EM29]`, `[JN30]`)

**Clarification in Deliverable:**  
> In the hybrid software stack, **Classical Shadows** is employed specifically as an information-theoretically efficient **observable reconstruction protocol** rather than an active hardware-level error mitigation scheme. By taking random Clifford or Pauli basis measurements, the Classical Shadows protocol enables the classical reconstruction of a large collection ($M$) of multi-qubit observables from only $\mathcal{O}(\log M)$ quantum measurements. On LUMI, Classical Shadows post-processing executes on CPU/GPU compute nodes to evaluate molecular Hamiltonians with significantly reduced QPU sample complexity, complementing error mitigation routines such as FiQCI-EMS.

### Section 4.1 & 4.2: LUMI Container Wrapper (Tykky) Details (Addressing Comments `[JK28]`, `[JT25]`, `[JN26]`)

To comply with the LUMI Lustre parallel file system policy, the WP2 release engineering workflow uses **Tykky**:
1. **Recipe Pinned Builds:** An environment recipe (`env.yml` / `requirements.txt`) defines Python 3.12 compatibility and points to the IT4Innovations private index (`https://opencode.it4i.eu/api/v4/projects/107/packages/pypi/simple`) for `qaas[iqm_qiskit]`, `iqm-client`, and `py4lexis`.
2. **Containerization:** Running `pip-containerize` or `conda-containerize` on LUMI encapsulates all dependencies into an immutable SquashFS container.
3. **Execution Wrappers:** Tykky generates lightweight wrapper scripts in the module's `bin/` directory, exposing python, ipython, and CLI commands seamlessly as if they were natively installed.
4. **Lmod Module:** The module definition sets up environment variables and adds the Tykky wrapper directory to `$PATH`.
